## 0. コンセプト（1行定義）

- **プランナー用（PC専用）**: 「このアプリのやり方をしていれば、売れるプランナーになれる」— アプリが商談の次の一手を常に指示する営業OS。
- **お客様用（スマホ専用PWA）**: 「スマホを触っていれば、結婚式の準備ができる」— 準備タスクが全部スマホで完結する。
- **AIヒヤリング**: 長めの診断型ヒヤリング（楽しんで受けられる体験）→ AIが最適プラン一式（テンプレ・MC台本込み）を生成。

## 1. リニューアルの範囲と方針

| 項目 | 決定 |
|---|---|
| 範囲 | **UI層のみ全面刷新**。DB・API・業務ロジック（進行表recalc・見積Ver管理・選曲・音響・freee等）は温存 |
| お客様側 | **PWA**（スマホ最適化Web・ホーム画面追加・App Store不要） |
| AI方式 | **併用**: 基本はMDファイル出力→外部AI→MD取り込み。将来Claude API組み込みできる設計（生成処理をアダプタ層に分離） |
| 宴会対応 | 案件タイプ（婚礼/宴会）で**自動切替**（用語辞書＋項目表示制御＋専用ヒヤリング＋専用テンプレ候補） |
| リポジトリ | 現行リポジトリ内で刷新（データ移行不要）。`src/app/(app)` = プランナーPC、`src/app/(customer)` = お客様スマホに再編 |

### 温存する既存資産（変えない）
- Prismaスキーマ・全APIルート（`src/app/api/v1/`）
- `src/lib/` の業務ロジック: rundown.ts / template-pack.ts / song-db.ts / cue-timings.ts / freee.ts / db-backup.ts
- 音響コンソール＋映像ウィンドウ（audio-console / live screen / BroadcastChannel）— 本番運用実績があるため画面はほぼ現状維持
- 認証（JWT / quickトークン / 承認フロー）

## 2. プランナー用アプリ（PC専用）

### 2.1 設計原則
1. **常に「次の一手」が画面に出ている**。プランナーが迷わない＝売れる行動が標準になる。
2. 1案件 = 1画面（案件コックピット）。タブ遷移地獄にしない。左に商談ステップナビ、中央に作業エリア、右に顧客攻略パネル。
3. PC専用に割り切る（最低幅1280px。レスポンシブ対応コードを持たない＝UIの複雑化を防ぐ）。

### 2.2 画面構成

```
┌─ グローバルナビ（案件一覧 / カレンダー / カタログ管理 / テンプレ管理 / 設定 / 自分の成績）
│
├─ ① ダッシュボード（ログイン直後）
│    今日の商談・打ち合わせ / 要対応アラート（承認待ち・回答期限） / 個人成績サマリ
│
├─ ② 案件コックピット（中核画面）
│    ┌──────────┬──────────────────┬──────────┐
│    │ 商談ステップ │  作業エリア          │ 顧客攻略     │
│    │ ナビ(左)    │  （ステップ連動で切替） │ パネル(右)   │
│    └──────────┴──────────────────┴──────────┘
│
└─ ③ 成果ダッシュボード（個人/店舗）
```

### 2.3 商談ステップナビ（左ペイン）— 「売れる型」の本体
案件タイプ別に標準ステップを定義。各ステップに **やること／トークポイント／確認漏れチェック／完了条件** を持たせる。

婚礼の標準ステップ（案）:
1. **初回接客** — ヒヤリング（AI診断つき）実施が完了条件
2. **会場見学** — 診断結果に基づく「刺さる見せ方」トークを右パネルに表示
3. **見積提示** — AIテンプレ適用→見積ウィザード。アップセル候補を提示
4. **成約** — 契約条件チェックリスト
5. **打ち合わせ1〜n** — 進行表・料理・席次・選曲・衣装（お客様スマホ側の入力状況が見える）
6. **最終確認** — 全項目確定チェック（未確定が赤で残る）
7. **当日** — 音響コンソール・進行表ライブ
8. **アフター** — 請求（freee連携）・アンケート回収

- ステップの完了条件はサーバーで判定（例: ヒヤリング未実施なら見学ステップに進んでも警告バッジ）。
- ステップ定義はマスタ化し、管理画面で編集可能（店舗の売り方に合わせて調整できる）。

### 2.4 顧客攻略パネル（右ペイン）
AIヒヤリングの診断結果から常時表示:
- **顧客タイプカード**: MBTIタイプ×生年月日系の複合。「この二人は◯◯タイプ」1行サマリ＋詳細
- **刺さる提案 / NG行動**: タイプ別の言い回し・重視ポイント・避けるべき提案
- **相性メモ（新郎×新婦）**: 意思決定の主導側・もめやすい論点 → 「決めの場面では新婦に最終確認を」等の実務ヒント
- **アップセル候補**: ヒヤリング回答×見積状況から「この顧客に響く追加提案」を根拠つきで最大3件（例: 「フォト重視回答→エンドロール撮影+8万」）。定価はサーバー強制（既存ルール踏襲）

### 2.5 成果ダッシュボード
- 個人別: 成約率・平均単価・アップセル成功率・打ち合わせ進捗遅延数
- ステップ別のボトルネック可視化（どのステップで失注しているか）
- データソースは既存の案件・見積データ。新規テーブルは失注理由の記録程度

### 2.6 その他プランナー画面
- テンプレ管理（pack読み込み・画像差し替え）、カタログ管理、会場・設備マスタ、承認待ちユーザー管理 — 機能は現行踏襲、UIだけ統一デザインに刷新

## 3. お客様用アプリ（スマホ専用PWA）

### 3.1 設計原則
1. **タスクフィード型ホーム**: 開くと「今やること」がカードで並ぶ（LINE的な気軽さ）。全機能メニューは下タブに格納。
2. 新郎・新婦が**別アカウント**（現行の2人ログインを正式仕様化）。誰が入力したか常に記録・表示。
3. 進捗が見える: 「準備完了度 62%」のようなゲージで、触るほど進む実感を出す。

### 3.2 画面構成（下タブ5つ・案）
| タブ | 内容 |
|---|---|
| 🏠 ホーム | 今やることカード（期限順）・準備完了度・式まであとN日 |
| 📋 準備 | 席次 / アンケート / 招待客リスト / 進行表閲覧 |
| 👗 えらぶ | ドレス・衣装 / 引き出物 / 料理 / 装花 …（カタログ連動） |
| 🔮 診断 | AIヒヤリング（後述）・診断結果の閲覧（二人の相性ページ等） |
| 💬 その他 | 会場からのお知らせ・プランナー連絡・アカウント |

### 3.3 席次入力（2人分担方式）
- 新郎アカウント=新郎側ゲスト、新婦アカウント=新婦側ゲストを入力（担当分担で衝突を構造的に回避）。
- 相手側は**閲覧のみ**（コメント可）。担当の入れ替え・代理入力はプランナーがPC側から許可切替できる。
- 入力はゲストリスト（名前・肩書・アレルギー⚠・子供/車椅子等）まで。**卓への配置はプランナーがPC側の席次エディタで行う**（既存seating-panelを流用）。お客様側は配置結果の閲覧＋「この人同士は近く/遠くに」の要望メモ。

### 3.4 アンケート（新郎用・新婦用）
- 同じ設問セットでも**新郎用・新婦用を別回答として保存**（比較できることが価値: 二人の回答ズレは相性診断とプランナー攻略パネルの材料になる）。
- 設問マスタはプランナー側で管理。回答状況はコックピットから見える。

### 3.5 えらぶ（ドレス・引き出物ほか）
- 既存カタログ（CatalogItem）をスマホ向けカードUIで表示。お気に入り→「これにする」で選択→プランナーに通知。
- **価格・確定はサーバー強制**（既存ルール）。お客様の「選択」は仮押さえ扱いで、見積反映はプランナーが承認して確定。
- 宴会モードではドレス等の婚礼カテゴリを非表示（カタログ項目に対象モードのフラグを持たせる）。

### 3.6 宴会モードのお客様画面
- 幹事（主催者）アカウント1つを基本（新郎/新婦の2人制は婚礼のみ）。
- 「準備」タブは席次・出欠・進行希望に絞り、診断は宴会用ヒヤリング（後述）に差し替え。

## 4. AIヒヤリング & テンプレ生成

### 4.1 体験設計 — 「楽しんで受けられる診断」
- 位置づけ: 事務的なフォームではなく**「ふたりの結婚式診断」というコンテンツ**。10〜15分の長めボリュームでも離脱しないよう:
  - 1問1画面のチャット/カード形式、進捗バー、途中セーブ
  - 章立て: ①ふたりのこと（生年月日・馴れ初め）→ ②性格診断（MBTI簡易設問 各12問程度）→ ③好み・価値観（演出・料理・雰囲気）→ ④予算・ゲスト構成
  - 章ごとに小さいご褒美画面（「新婦さまは ENFP・キャンドルが似合うタイプ🕯」等のミニ結果）を出して楽しさを維持
- 新郎・新婦**それぞれが自分のスマホで回答**（相性診断の入力になる）。
- 診断メニュー: **MBTI 16タイプ**＋**生年月日系（四柱推命・星座等）**＋**新郎×新婦相性診断**。統計学的な傾向コメント（「同じ回答傾向のカップルはガーデン演出の満足度が高い」等）は演出として文言に織り込む（本格的な統計エンジンは初期スコープ外）。

### 4.2 生成フロー（MD入出力・併用設計）
```
[ヒヤリング回答(2人分)]
   → ① アプリが「生成依頼MD」を出力（回答＋診断結果＋会場マスタ＋カタログ＋テンプレpack仕様を埋め込んだプロンプト）
   → ② 外部AI（ChatGPT/Claude）に貼り付け → テンプレ一式MD（pack形式）が返る
   → ③ アプリに取り込み（parsePack/scorePack 流用）→ プレビュー → 案件に適用
```
- 生成物（pack拡張）: 見積構成 / 進行表 / **MC台本（司会が読める文面・{新郎}{新婦}トークン込み）** / 選曲方針 / 演出提案 / **顧客攻略メモ（右パネル用）**
- ①②③の生成部分は `AiGenerator` インターフェースに切り出し、将来 `ClaudeApiGenerator` を差すだけでアプリ内自動生成に移行できる構造にする。
- プロンプトは現行 `template-pack-prompt.ts` を拡張。

### 4.3 2回目以降の取り込み（差分適用）
- 再ヒヤリング・再生成して取り込む際、**適用先を選択できる**:
  - ☑ 進行表・台本に反映
  - ☑ 演出・選曲提案に反映
  - ☐ **見積に反映**（金額が変わるため既定OFF。ONの場合は「新Ver作成」ルールに従い、確定済み見積は直接編集しない）
- 取り込み前に差分プレビュー（現在の内容 vs 生成案）を表示。

### 4.4 宴会用ヒヤリング
- 別設問セット: 会の目的（周年・表彰・歓送迎・ディナーショー）、主催者の狙い、格式、乾杯/挨拶の人数、余興有無、予算
- 診断は「主催者タイプ診断」（格式重視/盛り上がり重視/コスパ重視 等）に置き換え。MBTI等の個人診断は使わない。

## 6. 宴会モードの用語・表示制御

- 案件に `type: "wedding" | "banquet"` を持たせ（既存フィールドがあれば流用）、**全UI文言を用語辞書経由で出す**:

| 婚礼 | 宴会 |
|---|---|
| 新郎・新婦 | 主催者・代表者 |
| 新郎家／新婦家 | 主催側／来賓側（または非表示） |
| 挙式・披露宴 | 式典・宴会 |
| ご両家 | 主催者様 |
- 表示制御: 衣装・引き出物・両家項目・ケーキ入刀等の婚礼専用セクションは宴会案件で非表示。テンプレ・ヒヤリング・進行表シーン候補もtypeでフィルタ。
- **実装ルール: 画面に婚礼用語をハードコードしない**（必ず辞書関数 `t(key, caseType)` を通す）。これで「宴会に新婦家が出ちゃう」事故を構造的に防ぐ。

## 8. 【別件・要対応】カタログ消失の調査結果

**結論: コード・画面・導線はすべて無傷。データ（CatalogItemテーブル）が空 or 全件非公開になっている可能性が濃厚。**
- カタログはDBの `CatalogItem` が唯一のデータ源（シードなし）。0件だと画面ごと消える設計。
- コード上の削除口は「管理画面の🗑全カタログ削除ボタン」（実行時に `catalog-delete-N` という自動バックアップを作る）と、品目ごとの非公開トグル。
- **次の一手（本番での確認・要承認）**: ①本番DBの CatalogItem 件数確認 ②本番 `backups/` に `catalog-delete-*` があるか確認 → あれば削除ボタンが押された証拠で、`node scripts/restore-db.cjs` で復元可能。
